# 独立 API 测试框架实现计划

## 一、问题分析与核心思路

### 1.1 当前训练验证流程的耦合分析

当前 `_validate()` 的整个调用链路为：

```
RayPPOTrainer._validate()
  → TrajectoryCollector.multi_turn_loop(is_train=False)
    → vanilla_multi_turn_loop()
      → preprocess_batch()            # 将环境观测 tokenize 为模型输入
      → actor_rollout_wg.generate_sequences()  # ← 唯一接触模型的地方
      → tokenizer.batch_decode()       # 解码动作文本
      → envs.step()                    # 环境交互
    → gather_rollout_data()            # 收集轨迹
  → val_reward_fn(test_batch)          # 计算 reward
  → success_evaluator()               # 计算 success_rate
```

**关键发现**：整个多轮交互循环中，只有 `actor_rollout_wg.generate_sequences()` 这一个调用点涉及模型推理。其余所有组件（环境管理、观测预处理、轨迹收集、奖励计算）都是纯逻辑代码，完全可以复用。

### 1.2 解耦策略

训练流程中 `actor_rollout_wg` 是一个重量级的 Ray 分布式 Worker Group，内部包含 FSDP 模型 + vLLM 推理引擎。我们需要：

1. **创建一个轻量级的 `APIActorWrapper`**，实现与 `actor_rollout_wg` 相同的接口（鸭子类型），内部用 OpenAI-compatible API 替代本地模型推理
2. **直接复用** `TrajectoryCollector`、`make_envs()`、`EnvironmentManager`、`EpisodeRewardManager`
3. **跳过** 所有训练相关组件（critic、ref policy、advantage、optimizer 等）

## 三、各模块详细设计

### 3.1 `api_actor.py` — APIActorWrapper

这是整个方案中**唯一需要全新编写**的核心模块。它需要实现与 `actor_rollout_wg` 相同的鸭子类型接口。

#### 需要实现的接口

```python
class APIActorWrapper:
    """
    用 OpenAI-compatible API 替代分布式 Actor Worker Group。
    实现 TrajectoryCollector.vanilla_multi_turn_loop() 中所需的全部接口。
    """

    @property
    def world_size(self) -> int:
        """返回 1，消除 pad_dataproto_to_divisor 的影响"""

    def generate_sequences(self, prompts: DataProto) -> DataProto:
        """
        核心方法：接收 tokenized 输入，返回 tokenized 输出。

        输入 prompts.batch 中包含：
          - input_ids:      [batch_size, max_prompt_length]
          - attention_mask:  [batch_size, max_prompt_length]
          - position_ids:    [batch_size, (ndim,) max_prompt_length]

        输入 prompts.non_tensor_batch 中包含：
          - raw_prompt_ids:  List[List[int]]
          - data_source:     List[str]
          - (可选) raw_prompt: List[dict]  — 如果 return_raw_chat=True

        需要返回的 DataProto.batch：
          - prompts:         [batch_size, max_prompt_length]
          - responses:       [batch_size, max_response_length]  (右侧 pad)
          - input_ids:       [batch_size, max_prompt_length + max_response_length]
          - attention_mask:  [batch_size, max_prompt_length + max_response_length]
          - position_ids:    [batch_size, max_prompt_length + max_response_length]
        """
```

#### 内部处理流程（伪代码级别）

`generate_sequences` 内部需要完成以下步骤：

1. **Decode**：将 `input_ids` 通过 `tokenizer.decode()` 还原为文本 prompt
2. **构建 API messages**：根据 `raw_prompt`（如果有）或 decoded text 构建 `[{"role": "user", "content": ...}]`
3. **并发调用 API**：使用 `asyncio` + `aiohttp` 或 `openai` 库并发调用 OpenAI-compatible API 的 `/chat/completions` 端点。支持配置 `temperature`、`max_tokens`、`top_p` 等采样参数
4. **Tokenize response**：将 API 返回的文本 response 通过 tokenizer 编码为 token IDs
5. **构造输出张量**：
   - `responses`：response token IDs 右侧 pad 到 `max_response_length`
   - `prompts`：直接取输入的 `input_ids`（已经是 left-padded 的）
   - `input_ids`：拼接 `[prompts, responses]`
   - `attention_mask`：根据 pad token 生成
   - `position_ids`：根据 attention_mask 计算
6. **返回 DataProto**

#### 构造函数参数

```python
def __init__(
    self,
    tokenizer,                    # HF tokenizer 实例
    api_base_urls: List[str],     # API 端点列表（支持负载均衡）
    model_name: str,              # 模型名称
    api_key: str = "EMPTY",
    max_prompt_length: int = 4096,
    max_response_length: int = 2048,
    temperature: float = 0.4,
    top_p: float = 1.0,
    max_tokens: int = 2048,
    max_concurrent: int = 16,     # 最大并发请求数
    timeout: int = 120,
):
```

#### 关键实现注意事项

1. **张量维度对齐**：输出的 `prompts` 和 `responses` 的维度必须精确匹配 `max_prompt_length` 和 `max_response_length`，否则后续 `batch.union()` 时 TensorDict 会因维度不一致报错

2. **Pad Token 处理**：`prompts` 使用 left-padding（已由 `preprocess_batch` 处理），`responses` 使用 right-padding（与 vLLM rollout 行为一致）

3. **Response 截断**：如果 API 返回的 response tokenize 后超过 `max_response_length`，需要截断到该长度

4. **并发控制**：使用 `asyncio.Semaphore` 限制并发数，避免 API 过载。使用轮询策略在多个 `base_urls` 间分配请求

5. **错误重试**：API 调用失败时需要重试（建议 3 次），最终失败则返回空字符串对应的 token

6. **`raw_prompt` 优先**：如果 `non_tensor_batch` 中存在 `raw_prompt`（config 设置了 `return_raw_chat=True`，两个脚本均已开启），优先使用它构建 API 的 messages（保留完整的 chat 格式），而非从 `input_ids` decode。因为 decode 后的文本可能丢失特殊 token 信息

### 3.3 `eval_runner.py` — 评测入口

这是主控脚本，串联所有组件。

#### 主流程设计

```python
def main():
    """
    评测主流程，替代 RayPPOTrainer 中的训练+验证逻辑。
    只保留验证部分，用 APIActorWrapper 替代分布式 Actor。
    """
    # 1. 加载配置
    # 2. 初始化 Ray（轻量级，仅用于环境 workers）
    # 3. 初始化 Tokenizer（从 model.path 加载）
    # 4. 创建环境（调用 make_envs，只使用 val_envs）
    # 5. 创建 APIActorWrapper（传入 tokenizer + api config）
    # 6. 创建 TrajectoryCollector（传入 config + tokenizer）
    # 7. 创建 EpisodeRewardManager（传入 tokenizer）
    # 8. 运行评测循环
    # 9. 收集指标、打印结果、保存到文件
```

#### 评测循环的详细逻辑

评测循环需要复刻 `_validate()` (ray_trainer.py L953-L1090) 的核心逻辑，但去掉所有训练特有的部分：

```python
def run_evaluation(config, tokenizer, api_actor, traj_collector, val_envs, reward_fn):
    """
    核心评测循环。对标 RayPPOTrainer._validate()

    关键复用点：
    1. traj_collector.multi_turn_loop(
           gen_batch=...,
           actor_rollout_wg=api_actor,   # ← APIActorWrapper 替代
           envs=val_envs,                # ← 复用 make_envs 创建的 val_envs
           is_train=False
       )
    2. reward_fn(test_batch, return_dict=True)
    3. val_envs.success_evaluator(...)    # 隐含在 multi_turn_loop 内部

    需要处理的问题：
    - gen_batch 的构造：_validate() 中 gen_batch 来自 val_dataloader
      但 eval-only 模式下我们没有数据文件。
      解决方案：创建一个 DummyDataset 生成与环境数量匹配的占位 DataProto
    """
```

#### gen_batch 构造问题

在 `_validate()` 中，`test_data` 来自 `val_dataloader`，而 `val_dataloader` 的数据来自 `val_files` (parquet 文件)。这些数据包含初始 prompt 模板。

但在 eval-only 模式下，可能没有现成的 parquet 文件。需要分两种情况处理：

**方案 A（推荐）**：如果有 parquet 文件，直接复用 `create_rl_dataset` + DataLoader 的方式创建 `val_dataloader`，与训练流程完全一致。配置中通过 `data.val_files` 指定路径。

**方案 B**：如果没有 parquet 文件，需要创建一个 `DummyDataset`，为每个环境生成一个最小化的占位 DataProto。占位内容只需包含：
- `input_ids`：一个空 prompt 的 tokenized 形式（因为真正的 prompt 在 `preprocess_batch` 时会由环境观测重新生成）
- `attention_mask`
- `position_ids`
- `raw_prompt_ids`
- `data_source`：标识数据来源的字符串
- `raw_prompt`：空 chat 模板

推荐优先支持方案 A，方案 B 作为 fallback。

#### 指标收集

需要从评测结果中提取以下指标（对标 `_validate()` 的输出）：

- `success_rate`：总体成功率
- `test_score`：平均 episode reward
- `tool_call_count/mean`：平均工具调用次数
- ALFWorld 特有：按任务类型分类的成功率（`pick_and_place_success_rate` 等）
- SciWorld 特有：分场景成功率

## 四、关键实现要点与风险

### 4.1 `generate_sequences` 的输出格式

这是整个方案成败的关键。输出 DataProto 的张量维度必须与 vLLM rollout 的输出完全一致，否则后续 `batch.union()` 和 `gather_rollout_data()` 会出错。

具体而言，需要精确匹配以下维度规范（参考 [vllm_rollout.py L184-L340](file:///D:/WorkSpace/agent-verl/verl/workers/rollout/vllm_rollout/vllm_rollout.py#L184-L340)）：

| 字段 | Shape | 说明 |
|------|-------|------|
| `prompts` | `[B, max_prompt_length]` | 左侧 pad，与输入的 `input_ids` 相同 |
| `responses` | `[B, max_response_length]` | 右侧 pad，实际 token + pad token |
| `input_ids` | `[B, max_prompt_length + max_response_length]` | `cat([prompts, responses], dim=1)` |
| `attention_mask` | `[B, max_prompt_length + max_response_length]` | 非 pad 位置为 1 |
| `position_ids` | `[B, max_prompt_length + max_response_length]` | 从 0 递增（仅在有效位置） |

**编码时需要特别注意**：`position_ids` 在非多模态场景下为 `[B, seq_len]`，多模态场景下为 `[B, 4, seq_len]`。评测场景中如果只用文本环境（ALFWorld、SciWorld 均为纯文本），则使用 `[B, seq_len]` 即可。

### 4.2 与 `vanilla_multi_turn_loop` 的兼容性

审查 [rollout_loop.py L296-L519](file:///D:/WorkSpace/agent-verl/agent_system/multi_turn_rollout/rollout_loop.py#L296-L519) 中的 `vanilla_multi_turn_loop`，确认以下兼容性要求：

1. **`pad_dataproto_to_divisor(batch_input, actor_rollout_wg.world_size)`** (L373)
   - `APIActorWrapper.world_size = 1` → pad_size 始终为 0，等价于 no-op ✅

2. **`batch.union(batch_output)`** (L381)
   - 要求 `batch_output.batch` 与 `batch.batch` 的 batch_size 相同
   - `batch` 此时已经 pop 掉了 `input_ids`/`attention_mask`/`position_ids`
   - `batch_output` 需要提供这些字段的完整版（prompt+response 拼接后的）

3. **`tokenizer.batch_decode(batch.batch['responses'])`** (L383)
   - 要求 `responses` 是 valid token IDs ✅

4. **`batch.non_tensor_batch['uid']` / `batch.non_tensor_batch['traj_uid']`** (L378-L379)
   - 这些是在 union 之前设置的，与 generate_sequences 无关 ✅

### 4.3 `multi_turn_loop` 中 `is_train=False` 的路径

审查 [rollout_loop.py L593-L760](file:///D:/WorkSpace/agent-verl/agent_system/multi_turn_rollout/rollout_loop.py#L593-L760) 中的 `multi_turn_loop`：

当 `is_train=False` 时：
- 不调用 `gen_batch.repeat()`（L613 被跳过）
- 不使用 `dynamic_multi_turn_loop`（L616 条件不满足）
- 直接走 `vanilla_multi_turn_loop`（L626）
- 不保存 trajectory 到磁盘（L742 条件不满足）

但有几个 try-except 块会尝试导入 `rlvmr` 模块（L656, L674），如果该模块不存在会被 catch 住，不影响核心逻辑。✅

### 4.4 环境初始化的 Ray 依赖

`make_envs()` 内部调用 `build_alfworld_envs()` / `build_sciworld_envs()`，这些函数创建 Ray Actor 作为环境 worker。因此：

- **需要初始化 Ray**，但只需极少 CPU（`num_cpus` 参数按 `val_batch_size * resources_per_worker.num_cpus` 计算）
- **不需要 GPU**
- 建议在 `eval_runner.py` 中用 `ray.init(num_cpus=...)` 轻量启动

### 4.5 `gen_batch.meta_info` 的构造

在 `_validate()` (ray_trainer.py L996-L1003) 中，`test_gen_batch.meta_info` 被设置了以下字段：

```python
meta_info = {
    "eos_token_id": tokenizer.eos_token_id,
    "pad_token_id": tokenizer.pad_token_id,
    "recompute_log_prob": False,
    "do_sample": config...val_kwargs.do_sample,
    "validate": True,
}
```

`eval_runner.py` 中构造 gen_batch 时也需要设置这些字段，特别是 `eos_token_id` 和 `pad_token_id`，因为 `generate_sequences` 内部可能从 `meta_info` 读取这些值。

## 六、后续可扩展性

1. **多模型对比**：通过修改 `api.model_name` 和 `api.base_urls` 可以快速切换不同模型进行对比测试
2. **Checkpoint 评测**：将本地 checkpoint 用 vLLM/SGLang 启动为 API server，即可用同一框架评测训练过程中的 checkpoint
3. **批量评测**：可以包装一个外层脚本，遍历多组配置（不同 seed、不同环境）自动化运行
4. **新增环境**：只要新环境实现了 `EnvironmentManagerBase` 接口并注册到 `make_envs()`，即可无缝接入评测框架
